# Feature Interactions & Conflicts Audit

This document provides a deep-dive technical audit of the Udemy-Downloader-GUI codebase, specifically targeting the mechanics, conflicts, and resolution strategies for five core features: Sequence Locking, DRM Inspection, Course File Verification, Missing Downloads, and Concurrency Settings.

## 1. Under-the-Hood Workflow Mechanics

### 1.1 Sequence Locking & Indexing
- **Mechanism:** Sequence numbers dictate the prefixing of course, chapter, and lecture folders/files on disk (e.g., `1. Chapter/1. Lecture.mp4`).
- **Data Flow:** 
  - `getNextPermanentSequenceNumber()` calculates the next available integer by scanning existing courses in the DOM and `Settings.downloadedCourses`.
  - `assignSequenceNumberToCourse($course)` assigns this integer to a hidden input `<input name="sequence-number">` and the jQuery data object `$course.data("sequenceNumber")`.
  - During download, `utils.getSequenceName()` combines this sequence number with sanitized strings to map out the physical file paths.
- **State Updates:** Sequence numbers are persisted back to `Settings.downloadHistory` and `Settings.downloadedCourses` upon successful download initiation.

### 1.2 DRM Inspection (`checkDrmStatus`)
- **Mechanism:** Udemy protects certain premium video streams with Digital Rights Management (Widevine/FairPlay).
- **Data Flow:** `checkDrmStatus()` fetches the course curriculum JSON and iterates through all lectures. It checks the boolean flag `lecture.isEncrypted` and inspects the stream URL (`lecture.src`) for the substring `"encrypted-files"`.
- **State Updates:** If encrypted lectures are found, the count is stored in `<input name="encryptedvideos">`. The UI is updated to show a purple `[ DRM Protected ]` badge (`.course-encrypted`), and `$course.data("drmStatus")` is set to `"protected"`.

### 1.3 Course File Verification (`verifyCourseDownloads`)
- **Mechanism:** Scans the local disk to ensure all curriculum items exist and have a file size greater than zero.
- **Data Flow:** Re-fetches the curriculum tree, computes the expected paths via `utils.getSequenceName()`, and uses synchronous Node.js APIs (`fs.existsSync` and `fs.statSync(path).size === 0`) to check each file.
- **State Updates:** Items that fail the check are pushed to a `missingItems` array. The UI combined progress bar is updated to reflect the ratio of intact files vs total files, and a label displays `"Missing X files"`.

### 1.4 Missing Download Sync Button (`downloadMissingFiles`)
- **Mechanism:** Triggers a batch re-download exclusively for files that failed the verification check.
- **Data Flow:** Relies on the `missingItems` array generated by `verifyCourseDownloads()`. It filters out files that are flagged as DRM-protected (`drmBlockedCount`) and pushes the rest into a localized download queue.
- **State Updates:** Modifies `$course.data("isDownloading")` to `true`, disables the verification button, and visually resets the progress bars to only track the missing chunk.

### 1.5 Active Downloads Setting (`maxConcurrentDownloads`)
- **Mechanism:** Controls how many complete courses can be downloaded in parallel.
- **Data Flow:** Located in `Settings.download.downloadStartEnd`. The function `processDownloadQueue()` checks the current number of active courses (`activeCount`). If `activeCount < downloadStartEnd`, it pops the next queued course and fires `startDownload()`.
- **State Updates:** Enforces the limit at the *course* level, not the network request level.

## 2. Settings Conflicts & Feature Collisions

### 2.1 Concurrency vs. HLS Chunk Batching
**The Conflict:** The `maxConcurrentDownloads` setting restricts the number of *courses* downloading, but completely ignores the underlying network concurrency. When downloading HLS (.m3u8) video streams, the app spawns numerous parallel requests for `.ts` video segments. 
**The Edge Case:** If the user sets `maxConcurrentDownloads` to 3, and each course's M3U8 parser requests 50 chunks concurrently, the application opens 150 parallel HTTP sockets. This routinely leads to `EMFILE` (socket exhaustion) operating system errors, HTTP 429 Rate Limiting from Udemy's CDN, and silently dropped video chunks.

### 2.2 Sequence Locking vs. Partial Re-downloads
**The Conflict:** `getNextPermanentSequenceNumber()` aggressively recalculates sequence numbers based on the *current* DOM state.
**The Edge Case:** If a user clicks "Download Missing Files" on an older course that has fallen out of the active DOM (or if the `Settings.downloadHistory` was cleared), the app may assign a *new* sequence number to the course. As a result, the missing files will be downloaded into a newly prefixed folder (e.g., `45. React Course/...`) while the existing intact files remain in the old folder (`12. React Course/...`), fracturing the course on disk.

### 2.3 DRM Detection vs. Queue Verification
**The Conflict:** `verifyCourseDownloads()` expects a `.mp4` file for every video lecture. However, DRM-protected videos cannot be downloaded as `.mp4`.
**The Edge Case:** The verification loop flags all DRM-protected lectures as "Missing". The UI tells the user "Missing 10 files". The user clicks the missing sync button, which correctly skips the DRM files and finishes instantly. The user verifies again, and it still says "Missing 10 files". This creates an infinite, confusing loop for the user.

### 2.4 Asynchronous Disk Verification vs. Active Download Writes
**The Conflict:** `verifyCourseDownloads()` executes synchronously using `fs.statSync()`, while `mt-files-downloader` and `fs.appendFile` are asynchronously writing streams to disk.
**The Edge Case:** If a user clicks "Verify" while a course is actively downloading, the verification might hit a file that has been created but has `size === 0` for a few milliseconds, marking it as "Missing". Furthermore, verifying a large 500-lecture course synchronously completely blocks the Electron main/renderer threads, starving the active download streams and causing timeouts.

## 3. Conflict Resolution & Fix Strategy

### 3.1 Resolving DRM Verification Loops
**Solution:** Inject a DRM guard clause directly into the `verifyCourseDownloads` logic.
```javascript
// Before checking fs.existsSync, verify DRM status
if (lecture.isEncrypted || (lecture.src && String(lecture.src).includes("encrypted-files"))) {
    // Treat as "intact" or completely skip from missingItems to avoid false positives
    totalItemsChecked++;
    continue; 
}
```

### 3.2 Resolving Sequence Fracturing
**Solution:** Sequence locking must become immutable based on the file system, not the volatile DOM. Before assigning a new sequence number during a re-download, the app must run a Regex match against the target download directory to find if an existing folder already matches the `^\d+\.\s*CourseName` pattern, and lock onto that sequence number permanently.

### 3.3 Resolving Asynchronous Write Collisions
**Solution:** Implement a mutex lock via `$course.data("isDownloading")`.
```javascript
async function verifyCourseDownloads($course) {
    if ($course.data("isDownloading")) {
        dialogs.alert("Cannot verify a course while it is actively downloading.");
        return;
    }
    // ...
}
```

### 3.4 Resolving Concurrency Socket Exhaustion
**Solution:** Decouple course concurrency from network concurrency. Introduce a global `Semaphore` or `p-limit` queue for the M3U8 chunk downloader. Even if `maxConcurrentDownloads` is set to 5 courses, the global M3U8 semaphore should cap concurrent `.ts` segment downloads to a hard limit of `20` across the entire application, preventing CDN rate limits.

## 4. Architecture & Performance Improvements

Moving forward, Phase 2 and Phase 3 of our modernization roadmap should implement the following architectural upgrades for these subsystems:

*   **Migrate to Asynchronous I/O:** Replace all `fs.existsSync` and `fs.statSync` calls in `verifyCourseDownloads` with `fs.promises.stat` to prevent UI thread blocking during large course audits.
*   **Decoupled State Management:** Remove data attributes from the DOM (`$course.data("sequenceNumber")`). Implement a centralized Redux-style or MobX store for Course state, ensuring UI and file-system logic are not tightly coupled to HTML attributes.
*   **Dedicated Worker Threads for Disk I/O:** Move `verifyCourseDownloads` entirely out of the renderer process. It should be handled by a Node.js Worker Thread in the main process, communicating progress back to the renderer via IPC.
*   **Memory Stream Backpressure:** Upgrade the M3U8 downloader to utilize standard Node.js `stream.pipeline` with proper backpressure handling, avoiding excessive RAM usage when downloading massive 1080p chunks on slow storage drives.
*   **Resilient Network Retry Logic:** Implement exponential backoff for `downloadMissingFiles`. Currently, it retries immediately, which can result in a permanent ban from the CDN if a specific file is temporarily throwing 500 errors.
